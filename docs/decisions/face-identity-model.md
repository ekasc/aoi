# Face identity model

Status: SFace prototype engine reference-checked on CPU and through the physical iPhone's native pipeline on synthetic images. Not approved for production recognition accuracy.

## Decision

Prototype with OpenCV Zoo's original float32 SFace ONNX model. Prefer ONNX Runtime over converting these weights to TFLite or Core ML before establishing reference outputs. Do not install a runtime or ship weights until alignment and reference-parity tests are ready.

The model directory explicitly states, "All files in this directory are licensed under Apache 2.0 License." This covers the published model directory more clearly than a repository code license alone. Retain its license and applicable notices if weights are redistributed. This is the publisher's licensing statement, not a legal determination of training-data or biometric-consent rights.

Reject InsightFace's distributed recognition weights for this prototype. Its README separates MIT code from models and training data, which are "available for non-commercial research purposes only." A paid Aoi app cannot infer permission to use those weights from the code's MIT license.

## Preprocessing constraint

The [OpenCV reference implementation](https://github.com/opencv/opencv/blob/237b3c2eac474f3e69b8abff4c47384be1a9e521/modules/objdetect/src/face_recognize.cpp) aligns five facial landmarks with a similarity transform and warps to 112 by 112 pixels using linear interpolation. Its feature method builds a blob with scale 1, zero mean, and channel swap from OpenCV BGR to RGB. A mobile implementation must match that reference rather than guessing common face-model normalization.

The Apple Vision module now returns contours and proposed five-point estimates. Resizing a rectangle to 112 by 112 is not equivalent to the reference alignment. Landmarks, orientation, image sampling, and channel order must be correct before embeddings mean anything. The contour mapping must still be checked on real faces against the reference convention; synthetic pixel-warp parity does not prove equivalent face landmarks.

The model README describes MobileFaceNet instances trained with SFace loss, not generic ArcFace weights. Binary inspection and CPU execution verified input `data:float32[1,3,112,112]` and output `fc1:float32[1,128]`. Native phone runtime support remains unverified.

## Runtime candidate

`onnxruntime-react-native` 1.24.3 was the npm `latest` version checked. It is MIT-licensed, has a published Expo config plugin, and supports ONNX inference on iOS and Android. Its broad React Native peer range does not prove compatibility with Aoi's Expo 57, React 19, or React Native 0.86.3. Native compilation and session creation are acceptance gates.

- [Runtime documentation](https://github.com/microsoft/onnxruntime/blob/main/js/react_native/README.md)
- [Published package metadata](https://unpkg.com/onnxruntime-react-native@1.24.3/package.json)
- [Published Expo plugin](https://unpkg.com/onnxruntime-react-native@1.24.3/app.plugin.js)

`react-native-fast-tflite` is not chosen for this artifact because the published candidate is ONNX. Conversion would add a separate numerical-parity and licensing-provenance step without a proven benefit yet.

## Acceptance before recognition is exposed

1. Obtain the exact artifact, verify its size and SHA-256, and retain required license notices.
2. Inspect tensor signatures and run reference OpenCV embeddings on consented, labelled local fixtures.
3. Implement five-point alignment and compare crops and embeddings against the reference.
4. Prove native runtime compatibility, latency, memory use, and release of image/model resources.
5. Enroll both distinct identities locally with explicit consent and a way to remove their faceprints.
6. Measure pair precision and missed matches on a consented real library, including small/blurred faces, groups, similar faces, orientation changes, and both people independently.

The upstream demo uses a cosine threshold of 0.363. Aoi's helper currently defaults to 0.72. Neither is a validated product threshold. Do not silently copy the demo threshold or describe 0.72 as calibrated. The model, alignment version, enrollment data, and threshold must be validated together.
