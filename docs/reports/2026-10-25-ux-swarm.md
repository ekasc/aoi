## What the swarm is, and is not

Each comment is a **hypothesis from a fictional person**, not a reproduced defect. I checked the claims against the current source before promoting one to a finding. Findings below are source-verified unless marked otherwise.

This run did not use a device or simulator, so it does not prove native behaviour, VoiceOver output, Dynamic Type layout, or the feel of a transition.

## P1 — trust and pairing

### 1. A delivered memory briefly says it could not be sent

`components/moments/pending-memory-row.tsx:40-44`

The status line handles `sending` and `queued`, then falls through to `record.errorMessage ?? 'Could not send yet.'`. A `delivered` record has neither branch, so its row reads **“Could not send yet.”** while the line below reads **“Kept in your story.”** (`:106`). The row stays until the timeline acknowledges the real moment.

This is a contradiction at the exact moment the person wants proof the save worked. Add an explicit `delivered` branch (“Kept in your story.” / “Sent”) and keep the lower line consistent.

Representative comment:

> “A checkmark that lies is worse than no checkmark at all.” — Vera, critical tier

### 2. Setup never says which account is about to join or create

`components/setup/onboarding-wizard.tsx:969-975`, `:700`

The setup header shows only “aoi” and a folio number. The only account-adjacent control is “Wrong space? Sign out.” The signed-in user is available in the flow, but the screen never renders the name or email.

On a shared phone, or with two Google accounts, this is how a person joins the wrong space. The earlier dev-worker investigation hit exactly this class of confusion. Show **“Signed in as …”** with a switch-account action before the create/join decision, and repeat it on the join step.

### 3. An invite link opened while already in a space is silently dropped

`app/_layout.tsx:150-155`, `components/setup/onboarding-wizard.tsx:888`

The root layout routes any invite link to space setup. If the person already has a space, `skipToStory` redirects straight to Memories. The code is never shown, never redeemed, and never refused with a reason.

The inviter reasonably concludes the link connected them; the recipient sees their own existing archive. If the invite belongs to another space, say so plainly: **“You’re already in [space]. This invite is for [other space]. Leave your current space first, or ask them to join you.”** If the person is already in the invited space, say “You’re already connected” and open it.

### 4. First archive creation still does not show the recovery phrase

`app/(app)/album/recovery-phrase.tsx`, `features/album/protocol-archive.ts:178`

Archive creation is implicit. The phrase screen only reads entropy that already exists; it is reachable from Account after creation. A person can create the encrypted archive without ever being shown the one thing that restores it.

The normal-tier and critical-tier conversations both returned to this: the phrase is discovered only after it matters. A post-create, one-time phrase surface with a required paper confirmation belongs in the creation flow.

### 5. There is no enrolled-device list or revoke action

`app/(app)/album/devices.tsx`

The screen handles pending enrolment claims and approval. It does not list devices already trusted, and it offers no way to revoke one. Replacing a phone therefore leaves the old device’s access unexamined.

This is a protocol/UI gap, not a copy fix. It needs an enrolled-device read path and a signed revocation action before the screen can honestly say “manage devices.”

## P2 — state clarity and recovery

### 6. The join button is disabled with no visible reason

`components/setup/onboarding-wizard.tsx:683-698`

`Join space` is disabled while `!flow.canJoin`. The error line only receives text from `submitJoin`, but a disabled button cannot submit. A five-character code therefore produces a dead button and no explanation.

Either keep the button enabled and validate on press, or show a quiet line under the field: **“Enter all six characters to join.”** The six boxes make the shape visible, but they do not say why the action is unavailable.

### 7. Restore has no busy state

`app/(app)/album/restore.tsx:89-93`

`Restore this album` becomes disabled while `busy`, but its label does not change and there is no live region. A slow key derivation or network call looks like a dead button. Use **“Restoring…”**, `accessibilityState={{ busy }}`, and a polite announcement. Keep the typed phrase visible throughout.

The error split is already good: invalid phrase and unreachable archive are different messages.

### 8. The sky-versus-memories distinction lives in a help panel, not at the action

`app/(app)/(tabs)/together.tsx:165`

The help copy is explicit: “Photos chosen here stay in your sky. Add dated memories in Memories.” The action itself is a floating **“Choose photos”** button. A person who taps it from the shared sky can still believe they are adding a dated memory.

Put the destination in the action or its immediate helper: **“Choose photos for your sky”** on Us, and **“Add a memory”** on Memories. The current help text is good; it is just one tap too late.

## What held up well

These were frequent persona assumptions that the current code contradicts:

- **Plus scope is explicit.** The paywall says “One purchase covers both of you,” and the active state says “Plus is active on your shared Space” (`app/(app)/paywall.tsx:25`, `:154`).
- **Storage is counted.** Account and paywall show used and limit bytes.
- **Pending saves are distinct.** The composer queues a record, the feed pins it, and the row says “Waiting to send” or “Only visible to you until sent.” Authorship is rendered from the record (`components/moments/moment-card.tsx:123-126`).
- **The recovery phrase is text, not an image.** Each word has its own accessibility label; the claim that VoiceOver had nothing to read is false for the current screen.
- **Restore distinguishes a bad phrase from an unreachable archive.**
- **No fake progress bar was found in the recovery path.**
- **The static accessibility contract is clean** (`pnpm run a11y:audit`: 0 findings), and there are no font-scaling caps.

## Tier notes

**Normal users** want plain language, a visible account identity, and a receipt of what changed. They do not read secondary explanations. The strongest normal-tier finding is the missing account identity, followed by the first-create phrase.

**Frontend developers** focused on state visibility: disabled reasons, destination labels, delivered-versus-pending copy, busy states, and labels that survive large text. Most of their concerns map to the P1/P2 items above rather than new architecture.

**Weirdly super critical users** produced the most hypotheses, including several false positives: the phrase is not an image, Plus scope is stated, and the composer does not claim a queued save is delivered. Their useful contribution is the insistence on one canonical state string and an explicit account/device boundary.

## Recommended order

1. Fix the delivered-row contradiction (small, high trust).
2. Show the signed-in account on setup, and explain an invite that cannot be redeemed.
3. Give the join button a reason when it is unavailable.
4. Put the recovery phrase in the first archive creation, and add device revocation.
5. Add the restore busy label and put the sky/memories destination at the action.
